# What memory costs in tokens

<p className="lead">
	In real Claude Code sessions on this repo, the sessions with chamoji set up
	used fewer input tokens in total than the sessions without it, and usually
	answered in one turn. A replay with no model, which assumes that an agent with
	git alone reads the whole log, gives a far larger gap. Real agents search and
	don’t read everything, so the replay is a ceiling and not what a session
	spends. This page shows both, how we measured them, and what they don’t tell
	you.
</p>

## What a context switch is {{ icon: 'arrow-counter-clockwise' }}

A context switch is the moment an agent starts a session on a project it doesn’t remember. It needs two things before it can change anything safely:

- **What stands.** The rules and limits that still hold: constraints, gotchas and follow-ups that haven’t ended.
- **Why a line is the way it is.** The reason behind a line it is about to touch, so it doesn’t undo something on purpose.

With chamoji, what stands is the brief, which [`chamoji memory brief`](/commands/memory) prints and the session hook hands each new session. Why is [`chamoji why`](/commands/why) for one line. In the replay we assume that with git alone, what stands is the whole log, and why is the commit that last wrote the line, read in full or as its message only.

## How the replay measures {{ icon: 'sliders' }}

The replay runs no model. It counts the text each command prints, in estimated tokens:

- **What stands, with chamoji:** the output of `chamoji memory brief`, cut to its default budget as a session gets it, and the tool definitions of chamoji’s MCP server: the `tools` of its `tools/list` reply. `chamoji init --agents` registers that server, so its tool definitions are sent with every request of a session, and the chamoji side of the typical switch includes them.
- **What stands, with git alone:** the output of `git log --no-color`, in git’s default format.
- **One why, with chamoji:** the output of `chamoji why <file>:<line>`.
- **One why, with git alone, read in full:** `git blame -w -M` names the commit that wrote the line, which is how `chamoji why` finds it, and then `git show --no-color <commit>` is the text read: the message and the whole diff.
- **One why, with git alone, messages only:** the same commit read with `git show -s --no-color <commit>`: its header and message, without the diff. The card `chamoji why` prints is read from that message, so this is the like-for-like answer.

Three more figures are there for scale and are not part of the comparison:

- **The uncut brief:** `chamoji memory brief` at its largest budget, which is what the brief would list without the cut.
- **The history of the file:** `git log -p --no-color -- <file>`, which is what an agent reads if it asks for everything that happened to the file.
- **A notes file:** every line in `chamoji memory brief --json`, in every state, written as `Constraint: …`, `Gotcha: …` or `Follow-up: …`, one to a line. It is what you would have if you kept the same rules by hand in a file in the repo. It is never the headline: the headline compares chamoji with git alone.

The why figures come from a fixed sample of lines, each chosen because its commit has a card and the line still stands. The sample is in the repo, so a run measures the same lines every time. A typical switch is what stands plus a few why lookups, each at the mean cost of one why. The tables say how many.

The git commands run with a default git config and without git’s diff options from the environment, so a setting on the machine that runs them, such as a diff or log format, can’t change a figure.

## The replay: reading everything {{ icon: 'hash' }}

Measured at commit `61f7810` on 2026-11-19 UTC. Every figure is an estimate at 4 characters a token, rounded half up to whole tokens. No exact count has been made yet, so the estimate of 4 characters a token has not been checked against a model’s own count.

### What stands

With chamoji, what stands is the brief. `chamoji memory brief` cuts it to a budget of 1,500 tokens by default: on this repo it lists 32 of the 57 card lines, and each section says how many more it has. With a budget of 20,000 tokens it lists 57 of them in 2,425 tokens. All 57 card lines are open, so rule states made no difference to any figure here.

`chamoji init --agents` also registers chamoji’s MCP server, whose tool definitions are sent with every request of a session: 1,144 tokens. The replay counts them on the chamoji side. With git alone, it counts the whole log: 58,983 tokens for 457 commits.

### A typical switch

A typical switch is what stands, plus 5 why lookups at the mean cost of one. With chamoji a why is `chamoji why`. With git alone it is the commit that last wrote the line, read in full or as its message only.

|                          | What stands | Tool definitions | One why, mean | Typical switch |
| ------------------------ | ----------: | ---------------: | ------------: | -------------: |
| With chamoji             |       1,484 |            1,144 |          67.8 |          2,967 |
| Git alone, read in full  |      58,983 |                0 |       3,637.1 |         77,169 |
| Git alone, messages only |      58,983 |                0 |         121.7 |         59,592 |

Read in full, git alone comes to 26.0× as many tokens as chamoji, 74,202 more. With only each commit’s message for a why, it comes to 20.1× as many, 56,625 more.

## What the numbers don’t say {{ icon: 'info' }}

- **They are estimates.** A token here is four characters, counted as the text’s length divided by four and rounded up. A model’s own tokenizer gives other counts. Where a table says exact, a model counted them; every other figure is an estimate.
- **The replay counts what an agent would read if it read all of it.** Real sessions search, and the live sample shows what they spent. Neither says whether an answer was right: a smaller read is cheaper and leaves more room, and it can still be the wrong read.
- **The replay and the live sample measure different things.** The replay’s typical switch is one read of what stands plus five why lookups; a live session answers one question about a rule. Their ratios can’t be divided into each other.
- **The tokens saved are the same at any window size.** The window only changes the share: 250k, 500k and 1M tokens give the same saving and a different share of the window.
- **The older tags are read with the current build,** and the memory and notes refs are today’s at every tag, since they aren’t versioned by tag. The growth table shows how the repo’s history changed what stands, not how old releases of chamoji behaved.
- **On a young repo a notes file is about the size of the brief.** The default brief is the smaller of the two only because it is cut to its budget; the growth table shows the uncut brief beside it. A notes file keeps growing as rules are written, and it has no states: a rule that has ended still reads as true. It also can’t answer why a given line is the way it is, which is what the why figures measure.
- **One repo is one repo.** These are this project’s own commits, with its own mix of long and short messages. To run it on yours, build a chamoji checkout, then from inside your repo run `node <chamoji>/scripts/memory-benchmark.mjs --pick-sample --sample <file>` to pick a sample of your lines, and `node <chamoji>/scripts/memory-benchmark.mjs --sample <file>` to measure them.

## Run it yourself {{ icon: 'play' }}

From a full clone of the chamoji repo:

```bash {{ title: 'Measure' }}
pnpm benchmark:memory
```

It builds the CLI, measures in a throwaway clone under your temp folder, prints the tables and removes the clone. It makes no network call and needs no key. Measuring never writes to your checkout; the only things written there are the build output and what the flags below name.

<Properties>
	<Property name="--write" type="flag">
		Also writes the results to `docs/benchmarks/memory-tokens.json` and both
		data sections of this page.
	</Property>
	<Property name="--page-only" type="flag">
		Measures nothing and writes both data sections of this page from the two
		results files as they are. It can’t be combined with the other flags.
	</Property>
	<Property name="--exact" type="flag">
		Adds exact counts from a model’s token counter. It uses `ANTHROPIC_API_KEY`
		if one is set, and sends the measured texts to Anthropic; without one it
		skips the exact column and carries on.
	</Property>
	<Property name="--pick-sample" type="flag">
		Picks the sample of lines again and rewrites this repo’s sample file. With
		`--sample <file>` it picks a sample for the repo you run it in and writes it
		to that file. It can’t be combined with the other flags.
	</Property>
	<Property name="--sample <file>" type="path">
		Reads the sample from another file.
	</Property>
</Properties>

It needs the full history, so a shallow clone is refused with a message that says to fetch the rest.

The replay counts what an agent would read if it read all of it. To see what real sessions spend, ask Claude Code itself:

```bash {{ title: 'Ask real sessions' }}
pnpm benchmark:memory:live
```

It asks five questions about this repo, each with a known answer, three times in a clone with chamoji set up and three times in a plain clone, and writes what each session reported to `docs/benchmarks/memory-tokens-live.json`, with whether each question’s rule is in the default brief. Both sides get `Read`, `Grep`, `Glob` and `git` through Bash, and neither has the Edit or Write tools; only the chamoji side has its session hook, `chamoji` through Bash and chamoji’s MCP tools. It needs `claude` on your PATH and signed in, and it spends usage. Add `--dry-run` to ask the first question once on each side and write nothing. We mark each answer against its key by hand, then `pnpm benchmark:memory --page-only` puts the sample on this page without measuring the replay again.
