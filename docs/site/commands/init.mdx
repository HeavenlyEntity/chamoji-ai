# `chamoji init`

<p className="lead">
	Set this clone up to share project memory through `origin`, and take in what
	origin already has. With `--agents`, also connect Claude Code in this repo:
	the chamoji MCP server in `.mcp.json` and a commit hook in
	`.claude/settings.json`.
</p>

<Tag variant="setup">SETUP</Tag>
<Tag variant="setup">SINCE 0.11.0</Tag>
<Tag variant="changes">CHANGES YOUR REPO</Tag>

<Note>
	Git doesn’t clone chamoji’s memory ref, or the setting that fetches it, so
	every clone runs `chamoji init` once. It never pushes: `chamoji memory sync`
	shares what you have.
</Note>

## What it does, in order {{ tag: 'SETUP', variant: 'setup', label: 'chamoji init', icon: 'gear' }}

<Steps>
	<Step title="With --agents, checks both files.">
		`.mcp.json` and `.claude/settings.json` at the repo root, wherever you run
		it. Both are read and checked before either is written. If chamoji can’t
		safely change one, it changes neither, skips the memory step and exits 1.
	</Step>
	<Step title="With --agents, merges into them.">
		The MCP server and the commit hook, unless they’re there already. Your other
		entries are kept. Each file is replaced in one step, so a failure never
		leaves half a file.
	</Step>
	<Step title="Makes origin fetch memory.">
		Adds `+refs/chamoji/*:refs/chamoji/remotes/origin/*` to
		`remote.origin.fetch`, once. It leaves `remote.origin.push` alone, so a
		plain `git push` still pushes your branch. Without an `origin`, it says so
		and changes nothing.
	</Step>
	<Step title="Takes in origin’s memory.">
		Fetches it and merges it into yours, so a fresh clone needs nothing else. If
		the fetch fails, it says why on stderr, and the setting stays for the next
		`memory sync`.
	</Step>
</Steps>

After `init`, a plain `git fetch` or `git pull` also downloads origin’s memory, to a side ref that `chamoji memory` doesn’t read. `chamoji memory sync` takes it in. `chamoji release --push` syncs memory too, but only in a clone that ran `init`. Once per clone, outside CI, `init` ends with a one-line hint about `chamoji setup` on stderr.

[setup](/commands/setup) runs the same two steps as `setup memory` and `setup agents`, alongside the release settings and the commit composer hook.

## What --agents writes {{ icon: 'robot', badge: '2' }}

Both files are meant to be committed, so everyone who uses Claude Code in the repo gets the same setup. A changed file is written back as plain JSON with its indent kept, so other layout, such as blank lines, may differ.

<CodeGroup title="chamoji on your PATH">

```txt {{ title: '.mcp.json' }}
{
  "mcpServers": {
    "chamoji": {
      "command": "chamoji",
      "args": [
        "mcp"
      ]
    }
  }
}
```

```txt {{ title: '.claude/settings.json' }}
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "if": "Bash(git commit *)",
            "command": "chamoji agent-hook || true"
          }
        ]
      }
    ]
  }
}
```

</CodeGroup>

When `chamoji` isn’t on your PATH, the server starts with `npx --yes @chamoji/cli mcp` and the hook runs `npx --yes @chamoji/cli agent-hook || true`. A `node_modules/.bin` on the PATH doesn’t count, since npx and package scripts add one just for the run.

<Properties>
	<Property name=".mcp.json">
		Gets `mcpServers.chamoji`, which runs [`chamoji mcp`](/commands/mcp). A
		`chamoji` server that’s already there is yours to keep, whatever it runs.
	</Property>
	<Property name=".claude/settings.json">
		Gets an entry in `hooks.PreToolUse` that runs `chamoji agent-hook` before
		Claude Code’s Bash tool runs a `git commit`. Any entry whose command already
		runs `chamoji agent-hook` counts as there. The `|| true` is for a chamoji
		too old to know the hook: it would exit 2, which Claude Code reads as “block
		this”, and the file is shared.
	</Property>
</Properties>

Claude Code won’t start a server from a project’s `.mcp.json` until you approve it. Until then, `claude mcp list` shows it as pending approval.

chamoji leaves a file alone, and changes nothing, when it is a symlink or in a symlinked folder, isn’t valid JSON or a JSON object, has an `mcpServers`, `hooks` or `hooks.PreToolUse` of the wrong type, or holds a number that can’t be written back exactly.

<Note>
	On native Windows, the `.mcp.json` entry may need a `cmd /c` wrapper for `npx`
	or a `chamoji` shim. This hasn’t been tested there yet.
</Note>

## The commit hook {{ icon: 'git-commit' }}

`chamoji agent-hook` is the hook itself. Claude Code runs it before a Bash command and passes the command on stdin. When the command is a `git commit` whose message has no card line, it prints a denial, and the agent sees this reason:

```txt
Add why this change was made: put a "Why: <reason>" line at the end of the commit message, after a blank line. Constraint:, Gotcha: and Follow-up: lines are welcome too. Only if the user told you to skip this, prefix the command with CHAMOJI_NO_CARD=1.
```

It also denies a commit whose card is only `Why:` lines that don’t say why, judged by the rules in [What makes a good Why](/guides/writing-commits#what-makes-a-good-why). That reason starts `Your Why ("…") doesn't say why.`, then gives one sentence of advice, such as naming the bug, limit or request behind the change.

- **What counts:** any of `Why:`, `Constraint:`, `Gotcha:` or `Follow-up:`, below the subject paragraph, in `-m`, `--trailer` or a heredoc. A card with only `Why:` lines also needs that Why to give a reason; a `Constraint:`, `Gotcha:` or `Follow-up:` line is enough on its own. `-m "Why: because"` alone is a subject, not a card. A bare `git commit` has no message to read, so it’s denied too.
- **What passes:** `CHAMOJI_NO_CARD=1` in front of the command, which skips both checks, a message from a file or another commit (`-F`, `-C`), `--no-edit` with no new message, and commands that only look, such as `--dry-run` and `--help`. Every other command passes too.
- **What it can’t judge:** it judges only a Why it can read. A message from a file (`-F`) and a `Why:` with no space after the colon go through unjudged. A `$(...)` other than a `cat` heredoc is never run, so a card inside one can’t be seen: with no other card line, that commit is denied as having none.
- **What it can’t see:** it reads the command text, so a commit inside `sh -c '…'`, `xargs` or a shell alias isn’t checked.
- **It never blocks by failing:** whatever goes wrong, it prints nothing and exits 0, and the command goes through.

The hook covers Claude Code only. Other agents can use the MCP server, and write their cards by hand.

## Arguments

`chamoji init` takes no arguments. Extra words are ignored.

## Exit codes

<Properties>
	<Property name="0">
		Memory sharing is set up. Also when there is no `origin` to share with, and
		when the fetch from origin failed: the message says why.
	</Property>
	<Property name="1">
		`--agents` can’t safely change `.mcp.json` or `.claude/settings.json`, or
		can’t write one. Also outside a git repo, and anything else that fails.
	</Property>
</Properties>

`chamoji agent-hook` always exits 0. Its answer is what it prints. [Exit codes](/reference/exit-codes) has every command’s codes.
