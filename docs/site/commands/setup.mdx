# `chamoji setup`

<p className="lead">
	Set up a repo in one command: releases for each app or package, memory
	sharing, Claude Code and the commit composer. On a terminal it shows what it
	found and saves with Enter. Run it again to see where each step stands, or to
	change something.
</p>

<Tag variant="setup">SETUP</Tag>
<Tag variant="setup">SINCE 0.14.0</Tag>
<Tag variant="mono">MONOREPO-AWARE</Tag>
<Tag variant="ci">--json FOR CI AND AGENTS</Tag>

<Note>
	Setup never commits. It writes the `release` section of `chamoji.config.json`
	and, when you ask for them, a release workflow and `"private": true` in public
	apps. It shows each file first, and you review and commit them yourself.
</Note>

## What it does, in order {{ tag: 'SETUP', variant: 'setup', label: 'chamoji setup', icon: 'gear' }}

<Steps>
	<Step title="Looks at the repo.">
		Its apps and packages, version files, tags and remotes, from git and the
		files, with no AI. With the `gh` CLI and a GitHub `origin`, it also reads
		the repo’s squash-merge setting, and gives up on that after 5 seconds.
	</Step>
	<Step title="Says where each step stands.">
		With no step named, a line for releases, memory sharing, Claude Code and the
		hook: ✓ when it’s done, ○ when it isn’t, and – when it can’t run here. The
		setup screen shows these itself.
	</Step>
	<Step title="Asks.">
		On a terminal, the setup screen shows what it found and the questions the
		repo can’t answer. Enter saves, c changes something, and Esc cancels.
		Without a terminal and without `--yes`, it says what it would do and writes
		nothing.
	</Step>
	<Step title="Writes the release section.">
		The `release` section of `chamoji.config.json`. The file’s other keys are
		kept, and a section with nothing new is left untouched.
	</Step>
	<Step title="Writes the other release files.">
		The preview lists each one before anything is saved: the release workflow
		and the `package.json` edits, as set out in [Files setup
		writes](#files-setup-writes).
	</Step>
	<Step title="Runs the per-clone steps.">
		Memory sharing, Claude Code and the commit composer hook, the ones you
		picked. The hook is offered, never assumed.
	</Step>
</Steps>

[Set up a repo](/set-up-a-repo) walks through the screen, what setup looks for, and what each step writes.

## Arguments

<Properties>
	<Property name="step" type="releases | memory | agents | hook · optional">
		Run just this step, such as `chamoji setup releases`. Leave it out to run
		them all. Any other word exits 1. On a terminal, a named `memory`, `agents`
		or `hook` step runs without asking.
	</Property>
</Properties>

The four steps:

<Properties>
	<Property name="releases">
		Writes the `release` section. Named, it asks the release questions again,
		even when the section exists. A single package with no section is asked too,
		and gets one holding `trigger` and, for a public package, `publish`.
	</Property>
	<Property name="memory">
		Makes this clone share memory through `origin`, as `chamoji init` does. It’s
		offered only when there is an `origin`.
	</Property>
	<Property name="agents">
		Connects Claude Code: the MCP server in `.mcp.json` and a commit hook in
		`.claude/settings.json`. It’s offered when the repo has a `.claude` folder
		or `claude` is on your PATH.
	</Property>
	<Property name="hook">
		Installs the commit composer hook in this clone, as `chamoji hook install`
		does.
	</Property>
</Properties>

## The release questions {{ icon: 'gear' }}

Every repo, whatever its shape, is asked these, right after what it releases. Each has a recommended answer, so `--yes` takes them:

<Properties>
	<Property name="trigger" type="merge | manual">
		When a release happens: on merge to the default branch (the recommendation),
		or only when someone runs it. Setup reads the default branch from
		`origin/HEAD`, else the branch you’re on, else `main`. A section with no
		`trigger` is asked again on a re-run and counts as manual until you answer;
		nothing is written for it before then.
	</Property>
	<Property name="majors" type="auto | manual">
		Whether a breaking change releases on merge like any other change (`auto`,
		the recommendation), or waits for someone to release it.
	</Property>
	<Property name="publish" type="on | off">
		Whether to publish packages to npm. Only public libraries are offered; the
		question lists each with why it counts as one, such as ``library: `exports`
		field``, and names the apps it leaves out. A repo with only apps is never
		asked. Setup never asks about `publish.packages`, and keeps it as written.
	</Property>
	<Property name="publish.check" type="text">
		The command that must pass before publishing. It’s the root `check` and
		`test` scripts that exist, joined with `&&`, such as `pnpm check && pnpm
		test`; with neither, the `build` script; with none of them, no check, and
		setup says so.
	</Property>
	<Property name="privatize" type="ticks">
		Public apps to mark `"private": true` in their `package.json`, so a publish
		can’t pick them up. Unticked apps are left as they are. This is an edit to
		the app, not a config key.
	</Property>
	<Property name="ciAuth" type="oidc | token">
		How CI signs in to npm: trusted publishing (the recommendation) or an npm
		token. A package that publishes to another registry needs the token. This is
		not a config key either; it decides how the workflow file is written.
	</Property>
	<Property name="mentions" type="ticks">
		Version pins that tracked Markdown carries, such as `owner/repo@v1.2.0` or
		`@scope/name@1.2.0`, which each release moves to its new version. Setup
		offers the ones it finds, and asks nothing when there are none.
	</Property>
</Properties>

These keys need `"schema": 2`, so setup writes it with `trigger`, `majors` (when it isn’t `auto`), `publish` or `mentions`. A section with none of them stays at `"schema": 1`. Detection reads files only and never uses the network.

## Files setup writes {{ icon: 'file-code' }}

Besides `chamoji.config.json`, the releases step may write two more kinds of file. Each is shown in the preview and listed in `--json`’s `wrote`, and none is committed:

<Properties>
	<Property name=".github/workflows/chamoji-release.yml">
		The release workflow. It’s written when the trigger is `merge`, or
		publishing is on, and no tracked workflow in `.github/workflows` already
		runs chamoji’s release. A workflow counts when a step uses the Action or
		runs `chamoji release`, and it runs on a push to the default branch or on
		`workflow_dispatch`; a notes or PR-comment workflow that runs only on pull
		requests and tags doesn’t count. A section with no `trigger` counts as
		manual, so an old section doesn’t start releasing on its own: it gets no
		workflow until you answer the trigger. It pins the Action to the CLI version
		that wrote it. [The GitHub Action](/guides/github-action#release-on-merge)
		shows the file. When a workflow or a file is already there, setup never
		replaces it. It prints the trigger, permission and `with:` lines that
		workflow lacks, as `A workflow already runs chamoji (…); it needs:`, and
		nothing when it lacks none. `--json` lists the same lines in
		`workflowAdvice`.
	</Property>
	<Property name="package.json">
		`"private": true`, added after `"version"` (else after `"name"`) in each
		public app you ticked in the privatize question, keeping the file’s
		indentation. `--yes` takes the recommended tick, all of them.
	</Property>
</Properties>

Setup refuses to write through a symlink: if `package.json`, the workflow file or a folder above either is one, it stops with an error and writes nothing. In `--json`, `existingWorkflow` names the workflow that stood in for a new file, or is `null`.

## Flags {{ badge: '4', icon: 'flag' }}

<Properties>
	<Property name="--yes" type="boolean">
		Take every recommended answer without asking. It runs the memory and Claude
		Code steps when they’re offered and not done, and never installs the hook
		unless you name it: `chamoji setup hook --yes`. With a step, it runs just
		that step. Works with `--json` and `--explain`.
	</Property>
	<Property name="--json" type="boolean">
		Print what setup found and did as JSON on stdout, and nothing else. It never
		opens the screen. Without `--yes` it writes nothing and reports what it
		would do. With `--yes` it does it, then reports. The keys are `found`,
		`answers`, `why`, `steps`, `wrote`, `squashMerge`, `existingWorkflow` and
		`workflowAdvice`.
	</Property>
	<Property name="--explain" type="boolean">
		Print each value of the release section and where it came from: detected in
		the repo, recommended for its shape, chosen on the screen, or kept from
		`chamoji.config.json`. Works with or without `--yes`. Under `--json` it
		prints nothing more; the JSON’s `why` holds the same sources.
	</Property>
	<Property name="--no-update-check" type="boolean">
		Don’t check npm for a newer chamoji. See [the update
		notice](/install#the-update-notice).
	</Property>
</Properties>

## Output {{ icon: 'terminal-window' }}

These are from real runs in two small repos: `widgets`, a single package, and `shop`, with two apps and a shared package. The first run in `shop`, without `--yes` and with `--explain`, is on [Set up a repo](/set-up-a-repo#what-it-found).

A single package gets a release section too, holding when a release happens. Without a terminal, setup says what it would write and what else it would do, and exits 2:

```txt {{ title: 'chamoji setup' }}
○ releases aren't set up yet
– memory sharing needs a remote named origin
○ Claude Code isn't connected here yet
○ the commit composer hook isn't installed in this clone; chamoji setup hook --yes installs it

Found a single package; it keeps one version, as today. Releases happen on merge to main.

Setup would write this release section to chamoji.config.json:
{
  "schema": 2,
  "shape": "single",
  "trigger": "merge"
}

Setup would also connect Claude Code here, as chamoji init --agents does.
Setup would also offer the commit composer hook for this clone.
chamoji: setup needs a terminal to ask; run chamoji setup --yes to take every recommended answer
```

Naming the hook step is how `--yes` installs it:

```txt {{ title: 'chamoji setup hook --yes' }}
Installed the hook: /private/tmp/shop/.git/hooks/prepare-commit-msg
A plain `git commit` now opens the composer; -m, merges, amends and rebases are left alone.
```

Once everything is set up, a re-run only says so, and exits 0:

```txt {{ title: 'chamoji setup' }}
✓ releases are set up in chamoji.config.json
✓ memory sharing is on in this clone
✓ Claude Code is connected here
✓ the commit composer hook is installed in this clone

chamoji.config.json is already up to date.
```

## Exit codes

<Properties>
	<Property name="0">Setup saved, or nothing would change.</Property>
	<Property name="2">
		Something would change, but there is no terminal and no `--yes`, or there is
		`--json` and no `--yes`. Also when the hook step finds another tool’s hook
		and leaves it alone, and for a `release` section from a newer chamoji.
	</Property>
	<Property name="1">
		You cancelled, the step name is unknown, or a step failed, such as memory
		sharing that can’t reach `origin`. Also outside a git repo.
	</Property>
</Properties>
