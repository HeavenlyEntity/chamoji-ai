# `chamoji release`

<p className="lead">
	Cut a release from your git history. chamoji picks the version from your
	commits, writes the CHANGELOG.md section, bumps your version files, then makes
	the release commit and an annotated tag. Add `--push` to push it and create
	the GitHub release.
</p>

<Tag variant="changes">CHANGES YOUR REPO</Tag>
<Tag variant="mono">MONOREPO-AWARE</Tag>
<Tag variant="ci">--json FOR CI AND AGENTS</Tag>

<Note>
	In a monorepo, a version argument needs exactly one `--unit`: chamoji has to
	know which app or package the version is for.
</Note>

## What it does, in order {{ tag: 'CHANGES YOUR REPO', variant: 'changes', label: 'chamoji release', icon: 'rocket-launch' }}

<Steps>
	<Step title="Checks.">
		A clean working tree, the default branch when git knows `origin`’s, and the
		full history. A shallow clone is unshallowed, and tags are fetched from
		`origin` first.
	</Step>
	<Step title="Version.">
		The one next-version picks, or the one you give. The tag follows your tags’
		style, `v1.4.0` or `1.4.0`.
	</Step>
	<Step title="CHANGELOG.md.">
		The new section goes above the last release, below any Unreleased section,
		and older entries stay exactly as they are. A repo without the file gets one
		written from the whole history.
	</Step>
	<Step title="Version bumps.">
		Every tracked package.json, package-lock.json, pyproject.toml or Cargo.toml
		that carries the previous version. On a first release, every one that says
		another version.
	</Step>
	<Step title="Commit and tag.">
		A release commit in your repo’s style, such as `🔖 Release v1.4.0`, which
		later changelogs leave out, and an annotated tag. If anything fails before
		the tag exists, the repo is reset to where it started.
	</Step>
	<Step title="With --push.">
		Pushes HEAD and the tag, syncs project memory if `chamoji init` ran in this
		clone, then creates the GitHub release with the gh CLI. A failed push keeps
		the local release.
	</Step>
</Steps>

In a repo with release units, each unit with something to release gets its own version, tag and changelog, in one release commit. The units’ version files are bumped, and the others wait. [Monorepos](/guides/monorepos) explains which commits belong to which unit.

## Arguments

<Properties>
	<Property name="version" type="semver · optional">
		A version you choose, such as `2.0.0` or a prerelease like `2.0.0-rc.1`. It
		must be newer than the last release. Leave it out and chamoji picks one from
		the commits. Without release units, the first release needs one, since there
		is no tag to count from. In a monorepo it needs exactly one `--unit`.
	</Property>
</Properties>

## Flags {{ badge: '9', icon: 'flag' }}

<Properties>
	<Property name="--dry-run" type="boolean">
		Print the version, the files and the notes it would release, and write
		nothing. A dirty working tree is allowed; the other checks still run, and
		tags are still fetched. Wins over `--push`: nothing is committed, tagged or
		pushed.
	</Property>
	<Property name="--push" type="boolean">
		After the commit and tag, push HEAD and the tag to `origin`, sync memory if
		`chamoji init` ran here, and create the GitHub release with the gh CLI,
		marked as a prerelease for a prerelease version. Without gh, the push still
		happens and the output says the GitHub release was not created. In a
		monorepo it creates one GitHub release per tag, or one for all of them with
		`"githubReleases": "combined"`.
	</Property>
	<Property
		name="--unit <name>"
		type="string · repeatable · monorepos"
		since="0.13.0"
	>
		Release only these units, even when others have changes; the others stay
		waiting. Repeat it for several. A version argument needs exactly one. Only
		in a repo with release units; elsewhere, and for an unknown unit, it exits
		1.
	</Property>
	<Property name="--any-branch" type="boolean">
		Skip the check that you are on `origin`’s default branch, for release
		branches and hotfixes. The other checks still run.
	</Property>
	<Property name="--json" type="boolean">
		Print the result as JSON on stdout, for scripts, CI and agents, with a
		`status` of `dry-run`, `released` or `nothing`. Works with every other flag;
		exit codes stay the same.
	</Property>
	<Property name={'--trailer "Key: value"'} type="string · repeatable">
		Add a trailer line to the release commit. Repeat it for several lines.
		Ignored with `--dry-run`, which makes no commit.
	</Property>
	<Property name="--ai" type="boolean">
		Sort commits the rules can’t place with Jev, as `changelog --ai` does. Only
		changes how unplaced commits are grouped, and so the bump. Needs
		`TYPESAFE_API_KEY`, or it exits 1.
	</Property>
	<Property name="--config <file>" type="string · default chamoji.config.json">
		Read this config file instead. The default is `chamoji.config.json` when the
		repo has one. A file that doesn’t exist exits 1.
	</Property>
	<Property name="--no-update-check" type="boolean">
		Don’t check npm for a newer chamoji. See [the update
		notice](/install#the-update-notice).
	</Property>
</Properties>

To treat “nothing to release” as success in CI:

```bash
chamoji release --push || [ $? -eq 3 ]
```

## Exit codes

<Properties>
	<Property name="0">Released, or the dry run worked.</Property>
	<Property name="3">Nothing to release since the last tag.</Property>
	<Property name="2">
		A check failed: a dirty working tree, the wrong branch, a shallow clone it
		couldn’t unshallow, a version that isn’t semver or isn’t newer, a first
		release with no version, or a tag that already exists. Also for a `release`
		section from a newer chamoji.
	</Property>
	<Property name="1">
		Anything else, such as a failed push, an unknown unit, or a version without
		`--unit` in a monorepo.
	</Property>
</Properties>

[Exit codes](/reference/exit-codes) has every command’s codes.
