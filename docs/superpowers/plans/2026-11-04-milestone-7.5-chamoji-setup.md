# Milestone 7.5, part 2: `chamoji setup` implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `chamoji setup` works out how a repo is laid out and how it has been released, asks only what it can't work out, and shows the next release under the current answers. It writes the `release` section of `chamoji.config.json` and runs today's `init`, `init --agents` and `hook install` as its other three steps.

**Architecture:**

- **Detection and answers live in core,** in a new `packages/core/src/setup/` folder. Every function there is pure or reads git and files, and none of them prompts.
  - `detect.ts` covers the layout and versions.
  - `tags.ts` covers inherited, learned and stray tags.
  - `upstream.ts` covers the template remote, the starting point and squashed syncs.
  - `answers.ts` holds the answers model, the recommendations, the questions and the config section.
  - `preview.ts` holds the live preview and the replay. It reuses `planUnitReleases`, `unitChangelog` and `committedSection` from the 0.13.0 engine, with the candidate settings in memory.
- **The CLI** gets `packages/cli/src/setup/`:
  - `setup.ts`: flags, the four steps, `--yes`, `--json` and `--explain`, and writing files.
  - `screen.tsx`: the Ink screen.
  - `steps.ts`: the memory, agents and hook steps and their per-clone state.
- `init` keeps its output and becomes a thin caller of the same steps.

**Tech Stack:** TypeScript (ESM), Node 22 and 24, pnpm workspace (`@chamoji/core`, `@chamoji/cli`), Ink 8 and React 19 (as in the composer), `ink-testing-library`, vitest, meow.

**Spec:** [`docs/superpowers/specs/2026-11-03-monorepo-releases-and-setup-design.md`](../specs/2026-11-03-monorepo-releases-and-setup-design.md). This plan covers the spec's phase 2. Phase 1, the engine, shipped in 0.13.0 from [the engine plan](2026-11-03-milestone-7.5-monorepo-releases.md).

## Global Constraints

- **Setup never commits.** It writes files and says which ones; the developer reviews and commits them. `git restore chamoji.config.json` undoes the releases step.
- **Nothing changes for anyone who doesn't run setup.** `release`, `next-version` and `changelog` keep 0.13.0's output byte for byte. The compat goldens in `packages/cli/test/fixtures/compat-0.12/` keep passing unchanged.
- **`init` keeps its exact stdout, flags and exit codes.** Its one addition goes to stderr (Task 8).
- **Detection reads git and files only:** no network, no AI. The one network call is the optional squash-merge check through `gh`, and setup works the same without it.
- **The written `release` section must pass `parseReleaseSettings` unchanged,** and `release --dry-run` must accept it.
- **Interactive screens follow the terminal-face rules:**
  - stderr only;
  - no animation when stderr isn't a terminal, in CI, with `TERM=dumb`, with `--json` or with `CHAMOJI_NO_ANIMATION=1`;
  - the look follows `docs/brand/BRAND.md`.
- **Exit codes:**
  - 0 when saved, or when there was nothing to do;
  - 2 when there's no terminal and no `--yes`, or with `--json` and no `--yes` (it prints what it would do and writes nothing), and for `ConfigVersionError`;
  - 1 when cancelled ("Setup cancelled; nothing was saved.") and for other errors.
- **Exact copy,** used verbatim:
  - welcome line: `Run \`chamoji setup\` to get started.`
  - non-terminal line: `chamoji: setup needs a terminal to ask; run chamoji setup --yes to take every recommended answer`
  - composer impact line: `releases with: <units> · rides along to: <units>`
  - single-package line: `One package, so chamoji release already knows what to do; there's nothing to set up for releases.`
- **Paths are `/`-separated and relative to the repo root, on every OS.**
- **Workstream:** `monorepo-releases` (already active). Each commit uses gitmoji, carries `Workstream: monorepo-releases` and a `Why:` line, and ends with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- **Licensing:** no licensed font, icon or emoji-pack file goes in this repo. Setup's look uses only what `face.ts`, `faces.ts` and `foil.ts` already have.
- `pnpm check` and `pnpm test` pass on Ubuntu, macOS and Windows.
- **The release:** setup ships as 0.14.0, which the 0.13.0 monorepo hint already promises.

## Review Focus

1. **An app whose own tags look like the template's** (it tags plain `1.2.0`, and so does Makerkit). The ignore patterns must never hide the app's own releases. In that case, the inherited tags are ignored one by one. Tested in Task 2.
2. **Running setup again over a hand-written or older `release` section.**
   - The answers start from the existing section, not from fresh detection.
   - Keys setup doesn't ask about, such as `tags.aliases` or `githubReleases`, are kept.
   - An unchanged section isn't rewritten, and the message is "chamoji.config.json is already up to date".

   Tested in Tasks 4 and 6.

3. **A `chamoji.config.json` with other keys, tabs or 4-space indent, and no trailing newline.** Every other key and the indent survive the write. Tested in Task 4.
4. **A dirty tree, a branch other than the default, or a detached HEAD.** The preview still works (`allowDirty`, `anyBranch`, no fetch). It says "the next release from here would be", never an error. Tested in Task 5.
5. **A repo with no workspace, a single package, or no commits.** The releases step writes nothing and prints the single-package line. The other three steps still run. Tested in Tasks 1 and 6.

	path: string;

	path: string;
	version: string | null; // from its manifest
	versionFiles: string[]; // from detectVersionFiles, without its package.json
	/** Other tracked files under the unit holding its manifest version as a whole token; offered, never ticked. */
	otherVersionFiles: string[];
	easRemote: boolean; // appVersionSource: remote
	easLocal: boolean; // an eas.json with appVersionSource: local
};
export type LayoutDetection = {
	root: string;
	kind: 'single' | 'apps' | 'libraries' | 'mixed';
	packages: WorkspacePackage[];
	apps: AppCandidate[]; // empty unless kind is apps or mixed
	libraries: WorkspacePackage[]; // non-private packages, for libraries
	excluded: string[]; // unticked apps, plus tooling/* when it exists
	units: UnitFacts[]; // the ticked apps, or the libraries

- **Rules,** from the spec's Concepts section:
  - **Apps:** packages under `apps/*`, plus top-level packages that no other workspace package depends on and that are `private`.
  - **`kind`:**
    - `single` when there are 0 or 1 packages;
    - `apps` when there are apps and no non-private libraries;
    - `libraries` when there are non-private packages and no apps;
    - `mixed` when there are both.

    For `mixed`, setup treats the repo as `apps` and says that "mixed is coming". That's my call: the spec only says setup recognises it.

  - **`excluded`** gets the paths of unticked apps, plus `tooling/*` when a `tooling/` folder holds packages.
  - **`rootOnly`:** commits since the newest tag (or the last 200) whose files are all outside every package. `examples` holds up to 3 distinct file paths from them.
  - **`otherVersionFiles`:** files `git ls-files` lists under the unit's path, at most 500 of them, each under 256 KB and holding no NUL byte, whose text contains the manifest version with no digit or `.` on either side. Leave out `CHANGELOG.md`, lockfiles and the files in `versionFiles`. This is the spec's "Setup offers files where it finds the current version string".

**Files:**

- Produces:

```ts
export type TagDetection = {
	inherited: {tags: string[]; patterns: string[]; examples: string[]}; // patterns are tags.ignore regexes
	stray: {tags: string[]; patterns: string[]}; // e.g. wip/* -> '^wip/'
	perUnit: Record<
		string,
		{
			write: string; // recommended template
			read: string[]; // other formats its old tags use
			last: {tag: string; version: string} | null;
			unparseable: string[]; // tags naming the unit with no version
			manifestDisagrees: boolean; // last tag's version != manifest version
		}
	>;
};
export async function detectTags(
	layout: LayoutDetection,
	upstreamRemote: string | null,
): Promise<TagDetection>;
/** 'upstream' when it exists; else a remote other than origin whose fetched refs share history with HEAD; else null. Task 3 uses it too. */
export async function findUpstreamRemote(root: string): Promise<string | null>;
```

**Rules.** Which tags count as inherited is the builder's call in the spec. These are mine:

- **Inherited tags, with an upstream remote:** a version-like tag whose commit is reachable from `refs/remotes/<remote>/*`.
- **Inherited tags, without one:** a version-like tag that no recent author can reach. "Recent authors" are the authors of the newest 50 non-merge commits on HEAD that no version-like tag can reach. A tag counts as inherited when none of the commits it reaches was written by any of them.
- **Ignore patterns:**
  1. Turn each inherited tag into a shape: escape it, replace each run of digits with `\d+`, and anchor it with `^` and `$`.
  2. Remove duplicates.
  3. If a shape also matches a tag that isn't inherited, use one exact pattern per tag of that shape instead, such as `^4\.0\.2$` (Review Focus 1).
  4. `examples` holds the 3 newest inherited tags.
- **Stray tags:** tags that aren't version-like, match no unit template and aren't inherited. Their pattern is `^<first segment>/` when they share a `/` prefix, and the exact tag otherwise.
- **Learned formats:**
  - Strip a trailing version (`v?\d+(\.\d+)*(-[0-9A-Za-z.-]+)?`) from each tag that isn't ignored. The rest is the prefix.
  - The prefix must contain the unit's short name or its package name without the scope, case-insensitively, followed by a separator or the end of the prefix. If it does, the template is `<prefix>{version}`, keeping a literal `v`.
  - `write` is the template of the unit's newest tag. A unit with no tags gets the shape's default: `{unit}/v{version}` for apps and `{name}@{version}` for libraries.
  - `read` holds the unit's other templates.
- **Libraries that share one version:** when every non-private package has the same version and the repo has plain `v{version}` tags, the libraries get `write: 'v{version}'`. Task 4 then makes them one fixed group, as in chamoji-ai.

### Task 3: the template remote, starting point and squashed syncs

**Files:**

- Create: `packages/core/src/setup/upstream.ts`
- Test: `packages/core/test/setup/upstream.test.ts`

**Interfaces:**

- Produces:

```ts
export type UpstreamDetection = {
	remote: string | null; // 'upstream' if present; else another non-origin remote whose fetched refs share history with HEAD
	fetched: boolean; // the remote has fetched refs
	name: string | null; // suggested base name
	since: string | null; // full hash of the oldest own commit
	upstreamCommits: number; // reachable from HEAD and the remote
	syncs: number; // merges that bring upstream commits in
	squashedSyncs: string[]; // short hashes of commits that look like squashed syncs
};
export async function detectUpstream(
	root: string,
	remote: string | null, // from findUpstreamRemote (Task 2)
	inheritedTags: string[], // TagDetection.inherited.tags, for repos with no remote
): Promise<UpstreamDetection>;
```

**Rules:**

- **`since`:** the first entry of `git rev-list --reverse --topo-order HEAD --not --remotes=<remote>`.
- **`name`:** the remote URL's owner, title-cased (`makerkit` becomes `Makerkit`), or the repo name when there's no owner. My call: the spec says "the remote's repo name", but template repos are usually named after the product (`next-supabase-saas-kit-turbo`), while the owner is the brand, and the spec's example is "Makerkit". The developer can always change it.
- **A squashed sync:** a non-merge commit after `since` whose subject matches `/\b(merge|sync|update|pull)\b.*\b(upstream|<name>|template)\b/i`.
- **No remote:** everything is null or 0. A repo with inherited tags but no remote still gets `since`: the oldest commit, in topo order, that none of `inheritedTags` reaches.

  - `an upstream remote with nothing fetched is reported, and since stays null`.
  - `a squash-merged sync is listed`: the commit `🔀 Merge upstream Makerkit 4.0.3` is a plain commit.
  - `no remote and no inherited tags: nothing applies`.

```ts
export type Detection = {
	layout: LayoutDetection;
	tags: TagDetection;
	upstream: UpstreamDetection;
};
// detectLayout; then findUpstreamRemote; then detectTags(layout, remote); then detectUpstream(root, remote, tags.inherited.tags)
export async function detect(root: string): Promise<Detection>;
export type Source = 'detected' | 'recommended' | 'chosen' | 'kept';
export type SetupAnswers = {
	shape: 'single' | 'apps' | 'libraries';
	units: Array<{
		name: string;
		path: string;
		tag: string;
		read: string[];
		versionFiles: string[];
		buildNumber: 'untouched' | 'increment';
		firstVersion?: string;
		versioning: 'semver' | 'calver';
	}>;
	exclude: string[];
	sharedChanges: 'ride-along' | 'release-dependents';
	rootFiles: 'none' | 'all' | 'note';
	zeroMajor?: 'minor';
	fixed: string[][];
	upstream?: {remote?: string; name: string; since?: string};
	ignore: string[];
	rootChangelog: boolean;
	/** Hand-written keys setup doesn't ask about, carried through as written. */
	kept: Record<string, unknown>;
	why: Record<string, Source>; // keyed by question id
};
export function recommend(detection: Detection): SetupAnswers;
export function answersFromSection(
	section: unknown,
	detection: Detection,
): SetupAnswers; // re-runs
export type Question = {
	id: string; // 'shape' | 'units' | 'name:<unit>' | 'tag:<unit>' | 'ignore' | 'upstream.name' | 'sharedChanges' | 'rootFiles' | 'zeroMajor' | 'firstVersion:<unit>' | 'versionFiles:<unit>' | 'buildNumber:<unit>' | 'fixed' | 'rootChangelog' | 'alias:<tag>' | 'versioning:<unit>'
	title: string;
	found: string; // what chamoji found, in one sentence from the repo's own examples
	kind: 'choice' | 'ticks' | 'text';
	options: Array<{value: string; label: string; recommended?: boolean}>;
	needsAnswer: boolean; // false when detection settles it; such a question shows only under "Change something"
};
export function questions(
	detection: Detection,
	answers: SetupAnswers,
): Question[];
export function applyAnswer(
	answers: SetupAnswers,
	id: string,
	value: string | string[],
): SetupAnswers; // sets why[id] = 'chosen'
export function summary(detection: Detection, answers: SetupAnswers): string; // the first-screen paragraph
export function releaseSection(answers: SetupAnswers): Record<string, unknown>;
export function writeReleaseSection(
	original: string | null,
	section: Record<string, unknown>,
): {text: string; changed: boolean};
```

**Rules:**

- **The recommendations follow the spec.** For apps:
  - `sharedChanges: 'ride-along'`, `rootFiles: 'none'`;
  - `zeroMajor: 'minor'` only when some unit's version starts with `0.`;
  - `buildNumber: 'untouched'`;
  - no `firstVersion`, so the manifest's version is used.

  Libraries get `sharedChanges: 'release-dependents'`. When Task 2 gave the libraries one shared `v{version}` tag, they're one fixed group.

- **`needsAnswer` is true only for:**
  - `firstVersion:<unit>` for a unit with no tag;
  - `upstream.name` when there's a remote;
  - `zeroMajor` when a unit is at 0.x;
  - `buildNumber:<unit>` when `easLocal` is set;
  - `alias:<tag>` for unparseable tags.

  Everything else is detected, and is still listed under "Change something".

- **`found` copy** uses the repo's own examples. Exact example: `12 commits since your last release touched only pnpm-lock.yaml or .github/`.
- **`summary`** follows the spec's example exactly in form: `Found 4 apps (web, mobile, e2e, dev-tool) and 39 internal packages. web and mobile get their own versions; e2e, dev-tool and tooling are left out. 162 tags look like they came from Makerkit and will be ignored. Shared changes ride along with each app's own releases.` A clause with nothing in it is left out. Two clauses go at the end when they apply:
  - a unit whose last tag disagrees with its manifest: `web's last tag says 1.3.0 but apps/web/package.json says 0.1.0; the tag wins, and the release sets the file to the new version.`
  - squashed syncs: `2 commits look like squash-merged Makerkit syncs; they count as ordinary commits.`
- **`name:<unit>`** renames a unit. Its default is the folder's last segment. A name must match `^[a-z0-9][a-z0-9._-]*$` and be unique, or `applyAnswer` throws with that rule in the message.
- **`versionFiles:<unit>`** ticks `versionFiles` by default and lists `otherVersionFiles` unticked.
- **`releaseSection`:**
  - writes `schema: 1`, `shape`, `units`, `exclude`, `sharedChanges`, `rootFiles`, plus `zeroMajor`, `fixed`, `upstream`, `tags.ignore` and `rootChangelog` when they're set or not the default;
  - writes a unit's `read`, `versionFiles`, `buildNumber`, `firstVersion` and `versioning` only when they aren't the default;
  - merges `kept` back in, including `tags.aliases`.
- **`writeReleaseSection`:** parses `original` (or `{}`), sets `release` and leaves every other key. It renders with `renderJson` so indent and number spelling survive, adds a trailing newline only if `original` had one or was null, and sets `changed: false` when the text is unchanged.

export type ReplayLine = {
