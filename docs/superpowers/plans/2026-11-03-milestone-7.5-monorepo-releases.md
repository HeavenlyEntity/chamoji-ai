# Milestone 7.5: monorepo releases (the engine) implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `chamoji release`, `next-version` and `changelog` release each app or published package of a monorepo on its own, from a hand-written `release` section in `chamoji.config.json`. A repo without that section behaves exactly as with 0.12.0.

**Architecture:** A new `packages/core/src/units/` folder holds the engine, one file per concern:

- `settings.ts`: the settings
- `workspace.ts`: the packages
- `tags.ts`: tag templates and reading
- `attribute.ts`: which commits belong to which unit
- `upstream.ts`: template history
- `versions.ts`
- `version-files.ts`
- `notes.ts`: per-unit changelogs
- `plan.ts`: planning, applying and pushing a release

The single-repo path (`planRelease`, `buildChangelog`) is left alone. The CLI routes to `units/plan.ts` only when the config has a `release` section with a shape other than `single`. The `chamoji setup` command is a separate plan, written after this one lands.

**Tech Stack:** TypeScript (ESM), Node 22 and 24, pnpm workspace (`@chamoji/core`, `@chamoji/cli`), vitest, `semver` 7.8, `yaml` 2, meow, Bash for the Action.

**Spec:** [`docs/superpowers/specs/2026-11-03-monorepo-releases-and-setup-design.md`](../specs/2026-11-03-monorepo-releases-and-setup-design.md). This plan covers the spec's phase 1, plus the old-CLI guard from its Configuration section.

## Global Constraints

- **No `release` section, or `"shape": "single"`, means 0.12.0 behaviour byte for byte:** the same versions, tags, changelog, release commit, `--json` and `next-version` output. Nothing in `planRelease`, `buildChangelog`, `listReleaseTags` or the renderers may change their output for such a repo.
- **This milestone builds the `apps` and `libraries` shapes.** `train` and `mixed` are rejected with: `release.shape "<shape>" isn't supported yet; use apps or libraries`.
- **Old-CLI message, exact:** `this repo's release settings need chamoji 0.13.0 or newer`, exit code 2. The milestone ships as 0.13.0.
- **A commit's files decide which unit it belongs to.** Scopes and emoji never override files.
- **Paths are compared as `/`-separated strings relative to the repo root, on every OS,** and a path matches a unit only on a segment boundary (`apps/web` never matches `apps/web-admin`).
- **Deterministic and offline:** no network, and no AI deciding anything. `--ai` may sort commits as today.
- **Existing tags are never moved, deleted or renamed.** Manifests are edited as text, so formatting survives.
- **Defaults by shape:**
  - `apps`: `sharedChanges: "ride-along"`, `rootFiles: "none"`, tag `{unit}/v{version}`, a changelog in each unit's folder, GitHub releases per unit.
  - `libraries`: `sharedChanges: "release-dependents"`, `rootFiles: "none"`, tag `{name}@{version}`, a changelog in each unit's folder.
- **Config key for fixed version groups:** `release.fixed: string[][]`, by unit name. The spec writes `groups`, but `groups` already names changelog sections at the top level of `chamoji.config.json`, so the plan renames it to match changesets' `fixed`. Record this as a ruling in the ledger.
- **Commits** use gitmoji, carry `Workstream: monorepo-releases` and a `Why:` line, and end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- `pnpm check` and `pnpm test` pass on Ubuntu, macOS and Windows.

## Review Focus

1. **A unit path that is a prefix of another** (`apps/web` and `apps/web-admin`): commits to `apps/web-admin` must never count for `web`. Tested in Task 3.
2. **A file moved between packages:** a rename from `packages/ui/x.ts` to `apps/web/x.ts` counts for both the old and the new owner. Use `git log --no-renames` so both paths appear. Tested in Task 5.
3. **A unit tag on a branch not merged into HEAD:** it is ignored, as `listReleaseTags` does with `--merged`. Tested in Task 4.
4. **An Expo `app.config.ts` with `runtimeVersion` or a plugin option named `version`:** only the app's own top-level `version:` changes. When the current version isn't found, the release stops before writing anything. Tested in Task 8.
5. **Tag templates with regex characters** (`@acme/ui@{version}`, `release+{version}`): matching escapes the template. Tested in Task 4.

The rules, from the spec's "Which commits belong to which unit":

### Task 7: each unit's next version

**Files:**

**Interfaces:**

- Produces:

```ts
export type VersionInput = {
	unit: ResolvedUnit;
	last: UnitTag | null; // from unitTagHistory
	manifestVersion: string | null; // unit.pkg?.version
	commits: ParsedCommit[]; // own + shared (+ syncs) in the window
	today: string; // YYYY-MM-DD
	releasesThisMonth: number; // calver: this unit's tags in today's YYYY.MM
	zeroMajor?: 'minor';
};
export type NextVersion = {
	version: string;
	bump: SemverBump | 'prerelease' | 'first' | 'calver' | 'fixed';
} | null; // 'fixed': raised only to match its group
export function nextUnitVersion(input: VersionInput): NextVersion;
/** Fixed groups: every member gets the largest of the members' versions. */
export function alignFixed(
	next: Map<string, NextVersion>,
	fixed: string[][],
	current: Map<string, string | null>,
): Map<string, NextVersion>;
```

- Consumes: `UnitTag` from Task 4 and `ResolvedUnit` from Task 3. `bumpFor` and `nextVersion` from `version.ts`, unchanged.

The rules, from the spec:

- **First release:** with no `last`, the version is `firstVersion` when set, else `manifestVersion` as is, else `0.1.0`. It doesn't depend on the commits.
- **Tag wins:** with a `last`, bump from `last.version`, whatever the manifest says.
- **`zeroMajor: 'minor'`:** at major 0, a major bump becomes minor.
- **calver:** `YYYY.MM.N`, where N is `releasesThisMonth`, starting at 0.
- **Nothing to release:** null when the commits imply no bump. A first release still returns its version.
- **Fixed groups:** when any member releases, every member gets the highest version among the members' next versions and their current versions bumped by the largest bump.

  - `zeroMajor turns breaking into minor below 1.0`: `0.4.2` with a breaking commit gives `0.5.0`, and `1.4.2` gives `2.0.0`.
  - `calver counts this month's releases`: today `2026-11-03` with 2 earlier releases this month gives `2026.11.2`.
  - `no bump means null`.
  - `fixed groups share the larger version`: core `1.2.0` with a fix, and types `1.2.0` with no changes, both become `1.2.1`. A minor in either makes both `1.3.0`.

- Consumes: everything from Tasks 2 to 9. From `release.ts`: the dirty, branch, shallow and fetch checks (extract them into a shared `preflight(options)` without changing `planRelease`'s behaviour), `releaseSubject` and `ReleaseError`.

**How the plan is put together:**

1. Run the preflight, then `readWorkspace` and `resolveUnits`, then `listTags`.
2. For each unit:
   - find its last tag with `unitTagHistory`
   - work out its window: `last.tag..HEAD`, or `sinceRange`, or all of HEAD
   - read the window's commits and files
   - remove upstream commits and add syncs, as own commits when `syncFiles` touch the unit
   - attribute the rest
3. Decide which units release:
   - with own commits that imply a bump, or `units` naming the unit, or a `Release:` trailer in its window naming it
   - under `release-dependents`, also any unit with shared commits, and any library unit whose runtime dependency (a published unit) releases. That unit gets a patch release with a Dependencies line, and the range in its `package.json` set to `^<new version>`, unless the range starts with `workspace:`
4. Work out versions with `nextUnitVersion`, then `alignFixed`. `versions[unit]` overrides, and is checked as `planRelease` checks `version`.
5. Collect the changes:
   - each unit's changelog
   - its version-file edits
   - range edits
   - an optional root changelog that lists every release with links, when `rootChangelog`
6. The subject is `releaseSubject(recent, tags.join(', '))`.

Under `rootFiles: "note"`, each releasing unit's notes get the `Tooling and CI: <n> changes` line for the root commits in its window, and they never trigger a release. Under ride-along, ranges never change without a release of the dependent. `pending` lists units that aren't releasing but have shared commits waiting.

Units are planned and tagged in dependency order: a unit that another depends on comes first.

**Applying** writes the changes, makes one commit, and makes one annotated tag per unit, rolling back as `applyRelease` does. **Pushing** pushes `HEAD` and every tag by name in one `git push`.
